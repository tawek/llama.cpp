# Metrics Implementation Plan

## Goal

Expose five monotonic counters in the `/metrics` Prometheus endpoint so that
`llama-gui` can compute real-time rates by differencing successive samples:

| Counter              | Meaning                                           |
|----------------------|---------------------------------------------------|
| `n_tokens_pp_total`  | Prompt tokens decoded (updated per ubatch)        |
| `n_tokens_tg_total`  | Tokens returned to the user (spec + non-spec)     |
| `n_tokens_td_total`  | Draft tokens generated by the draft model         |
| `n_tokens_tda_total` | Draft tokens accepted by the target model         |
| `n_tokens_tdr_total` | Draft tokens rejected (n_td − n_tda)              |

The PP counter must increment **during** prompt processing, not only when the
first generated token appears.  That requires a callback fired by
`llama_decode()` after every micro-batch (ubatch).

---

## Design

### Thread model

All five counters are `std::atomic<uint64_t>` stored in `server_context_impl`.
The decode thread writes them with `memory_order_relaxed`.  The HTTP thread
reads them with `memory_order_relaxed` inside the `get_metrics` lambda (which
already captures `this`).  No mutex is needed.

### Why a callback instead of an external loop

`llama_decode()` splits its input batch into one or more ubatches internally
and runs each through the compute graph.  A 2048-token batch at `n_ubatch=512`
becomes four sequential ubatch calls, each taking ~2–3 s on a 35B CPU model.
The server loop cannot interpose between ubatches without restructuring the
batch fill logic.  A callback registered on the `llama_context` fires after
every ubatch completes, giving the right granularity with no server-side loop.

### PP callback signal

`n_outputs_all < n_tokens_all` is true for every prompt batch (only the last
token requests logits) and false for all pure-generation and speculative
verification batches (where every token requests logits).  This is the
condition used to gate the callback.

Mixed batches (prompt from one slot + 1 generation token from another slot
under `--cont-batching`) fire the callback with `ubatch.n_tokens` which
over-counts by at most 1 TG token per batch.  That is an acceptable
approximation; the TG counter is tracked separately and correctly via the
existing `slot.n_decoded` increment sites.

#### 4c. Register PP callback on ctx_tgt after model load

In `load_model()`, after `ctx_tgt = llama_init->context()` (~line 752):

```cpp
// Register per-ubatch PP callback so evt_n_tokens_pp updates during decode.
llama_set_pp_eval_callback(ctx_tgt, [](uint32_t n_tokens, void * ud) {
    auto * self = static_cast<server_context_impl *>(ud);
    self->evt_n_tokens_pp.fetch_add(n_tokens, std::memory_order_relaxed);
}, this);
```

`load_model()` is also called on sleep/resume, so the callback is automatically
re-registered whenever `ctx_tgt` is recreated.  No extra registration site needed.

```cpp
// Event-based monotonic counters — read directly (no task queue round-trip).
static const struct { const char * name; const char * help; } evt_defs[] = {
    { "n_tokens_pp_total",  "Total prompt tokens processed (event-based)."        },
    { "n_tokens_tg_total",  "Total generated tokens (event-based)."               },
    { "n_tokens_td_total",  "Total draft tokens generated (event-based)."         },
    { "n_tokens_tda_total", "Total draft tokens accepted (event-based)."          },
    { "n_tokens_tdr_total", "Total draft tokens rejected (event-based)."          },
};
const uint64_t evt_vals[] = {
    evt_n_tokens_pp .load(std::memory_order_relaxed),
    evt_n_tokens_tg .load(std::memory_order_relaxed),
    evt_n_tokens_td .load(std::memory_order_relaxed),
    evt_n_tokens_tda.load(std::memory_order_relaxed),
    evt_n_tokens_tdr.load(std::memory_order_relaxed),
};
for (size_t i = 0; i < 5; i++) {
    prometheus << "# HELP llamacpp:" << evt_defs[i].name << " " << evt_defs[i].help << "\n"
               << "# TYPE llamacpp:" << evt_defs[i].name << " counter\n"
               << "llamacpp:"        << evt_defs[i].name << " " << evt_vals[i]      << "\n";
}

res->data = prometheus.str();
```

The lambda already captures `this` so `evt_n_tokens_pp` etc. are accessible
without any reference change to the route setup.

## Risks and mitigations

| Risk | Mitigation |
|------|-----------|
| Mixed batch over-counts PP by ≤1 TG token | Acceptable; TG counted separately and correctly |
| Callback not re-registered after sleep/resume | Register in the same code path as `llama_set_abort_callback` |
| Counter reads by HTTP thread while decode thread writes | `std::atomic` with `relaxed` ordering is safe; stale reads are ≤ 1 ubatch old |
| `n_draft` out of scope at line 3263 | Confirmed in scope: `const size_t n_draft = slot.spec_draft.size()` is at line 3193, same enclosing block as line 3263 |
